# RedZone — ระบบรายงานเหตุการณ์และพื้นที่เสี่ยงในมหาวิทยาลัย

ต้นแบบเว็บแอปฝั่งผู้ใช้ (actor `User` ใน use case diagram) สำหรับวิชา System Analysis
เขียนด้วย HTML + CSS + JavaScript ล้วน ไม่ต้องติดตั้งอะไร ไม่ต้อง build
แผนที่ใช้ **Leaflet + OpenStreetMap** ซึ่งฟรี ไม่ต้องมี API key ไม่ต้องผูกบัตรเครดิต
ข้อมูลทั้งหมดเป็นข้อมูลจำลอง (mock data) ยังไม่ต้องมีฐานข้อมูล — แต่เตรียมโครง PHP + MySQL ไว้ให้แล้ว

---

## 1. เริ่มใช้งานใน VS Code

1. เปิด VS Code → `File` → `Open Folder...` → เลือกโฟลเดอร์ `redzone-project`
2. ติดตั้งส่วนขยาย **Live Server** (ผู้พัฒนา Ritwick Dey)
3. คลิกขวาที่ `index.html` → `Open with Live Server`

เบราว์เซอร์จะเปิดที่ `http://127.0.0.1:5500` และแก้ไฟล์แล้วรีเฟรชให้เองทันที

> ดับเบิลคลิกไฟล์ `index.html` ตรง ๆ ก็เปิดได้ แต่แนะนำ Live Server
> เพราะตอนต่อ PHP ทีหลังจะต้องเปิดผ่าน server อยู่แล้ว

### ส่วนขยาย VS Code ที่ช่วยงานนี้

| ส่วนขยาย | ช่วยอะไร |
|---|---|
| Live Server | เปิดเว็บและรีเฟรชอัตโนมัติ |
| Prettier | จัดรูปแบบโค้ดให้สวยด้วย `Shift+Alt+F` |
| Auto Rename Tag | แก้ tag เปิดแล้ว tag ปิดเปลี่ยนตาม |
| Error Lens | โชว์ error ตรงบรรทัดที่ผิดเลย |
| PHP Intelephense | เติมโค้ด PHP (ตอนทำ backend) |

## 4. เรื่องแผนที่ (Leaflet + OpenStreetMap)

**ทำไมไม่ใช้ Google Maps** — Google Maps ต้องสมัคร Google Cloud และผูกบัตรเครดิตก่อนจะขอ
API key ได้ ส่วน Leaflet เป็นไลบรารีโอเพนซอร์ส และ OpenStreetMap ให้ใช้แผ่นแผนที่ฟรี
สำหรับงานปริมาณน้อย เหมาะกับต้นแบบที่ใช้นำเสนอ ไม่มีค่าใช้จ่ายและไม่ต้องสมัครอะไรเลย

**ขอบเขตพื้นที่ให้บริการ: รัศมี 10 กม. รอบ มจพ.**
ระบบรับแจ้งเหตุทั้งในและนอกรั้วมหาวิทยาลัย เพราะจุดเสี่ยงจริงของนักศึกษาส่วนใหญ่
อยู่บนเส้นทางไป-กลับหอพักและจุดขึ้นรถ ไม่ใช่แค่ในรั้ว
แก้ค่าได้ที่ `RZ.SCOPE` ใน `assets/js/config.js` (`center` และ `radius` หน่วยเมตร)
แผนที่ถูกล็อกไม่ให้เลื่อนหรือซูมออกไปนอกวงนี้ และปักหมุดนอกวงไม่ได้ —
ถ้าคลิกนอกเขต จะขึ้นข้อความบอกระยะห่างและไม่ย้ายหมุด

**สิ่งที่แผนที่ทำได้ในต้นแบบนี้**

| ทำได้ | ทำที่ไหน |
|---|---|
| แสดงหมุดเหตุการณ์ตามระดับความเสี่ยง (แดง/เหลือง/เขียว) | `renderPins()` |
| เอาเมาส์ชี้หมุดเห็นชื่อเหตุการณ์ · คลิกหมุดเปิดการ์ดรายละเอียด | `renderPins()` |
| คลิกในรายการด้านขวา แผนที่เลื่อนไปหาหมุดนั้น | `focusIncident()` |
| ซูมเข้า-ออก (ปุ่ม + / − หรือเลื่อนล้อเมาส์) · ลากเลื่อนแผนที่ | Leaflet จัดการเอง |
| วงพื้นที่เสี่ยง รัศมีเป็นเมตรจริง คลิกดูจำนวนรายงาน | `renderZones()` |
| ปุ่ม "พื้นที่เสี่ยง" เปิด/ปิดวงได้ (ตอนนำเสนอจะโชว์หรือซ่อนก็ได้) | `#zoneToggle` |
| ปักหมุดตำแหน่งในฟอร์มแจ้งเหตุ — คลิกที่ไหนหมุดไปที่นั่น | `form.js` → `initPicker()` |
| วงขอบเขต 10 กม. + ล็อกแผนที่ไม่ให้เลื่อนออกนอกเขต | `drawScope()` |
| ตรวจว่าหมุดอยู่ในเขตไหม + บอกระยะห่างจาก มจพ. | `inScope()` / `distanceText()` |

**ต้องต่ออินเทอร์เน็ต** เพราะแผ่นแผนที่โหลดจากเซิร์ฟเวอร์ OpenStreetMap
ถ้าเน็ตล่มหรือเครือข่ายที่มหาวิทยาลัยบล็อก CDN เว็บจะไม่พัง — จะขึ้นข้อความ
"โหลดแผนที่ไม่ได้" แทนตัวแผนที่ ส่วนรายการเหตุการณ์ ฟอร์ม และคอมเมนต์ยังสาธิตได้ปกติ

> ถ้าเครือข่ายบล็อก cdnjs ให้โหลด 2 ไฟล์นี้เก็บไว้ในเครื่องก่อนวันนำเสนอ
> `leaflet.min.js` และ `leaflet.min.css` จาก https://leafletjs.com/download.html
> วางไว้ที่ `assets/vendor/` แล้วแก้ `<link>` กับ `<script>` ใน `index.html` ให้ชี้ไฟล์ในเครื่อง
> (ตัวแผ่นแผนที่ยังต้องใช้เน็ตอยู่ แต่จะไม่ค้างตอนโหลดไลบรารี)

**พิกัดที่ใส่ไว้เป็นตำแหน่งจำลอง** รอบพื้นที่ มจพ. บางซื่อ ถ้าต้องการพิกัดจริงของแต่ละจุด
เปิด openstreetmap.org หรือ Google Maps คลิกขวาที่จุดนั้นเพื่อคัดลอกพิกัด แล้วมาแก้ใน
`RZ.LOCATIONS` — แค่ดูพิกัดไม่ต้องใช้ API key

## 5. บทบาทผู้ใช้ (2 บทบาท)

ระบบมี 2 บทบาทเท่านั้น ตรงกับ use case diagram — `user` และ `admin`
(คอลัมน์ `users.role` ในฐานข้อมูล)

### ระบบทำงาน 2 โหมด (ตัดสินเองอัตโนมัติ)

| | โหมดต้นแบบ | โหมดจริง (live) |
|---|---|---|
| เกิดเมื่อ | เปิดไฟล์ตรง ๆ / Live Server (ไม่มี PHP) | เปิดผ่าน XAMPP หรือโฮสต์ |
| ข้อมูลอยู่ที่ | localStorage ของเบราว์เซอร์นั้น | ฐานข้อมูล MySQL |
| คนอื่นเห็นข้อมูลเราไหม | ไม่เห็น แยกกันคนละเครื่อง | เห็น ใช้ข้อมูลชุดเดียวกัน |
| รหัสผ่าน | เทียบตรง ๆ ใน JavaScript | `password_verify()` ที่เซิร์ฟเวอร์ |

เช็กว่าอยู่โหมดไหน — เปิด Console (F12) พิมพ์ `RZ.LIVE`
ขั้นตอนขึ้นโฮสต์อยู่ใน **`docs/hosting.md`**

**เปิดเว็บมาจะเจอหน้าเข้าสู่ระบบก่อนทุกครั้ง** ไม่มีทางลัดสำหรับสาธิตแล้ว
บทบาทมาจากบัญชีที่ล็อกอินสำเร็จ ผู้ใช้เลือกเองไม่ได้
(ปุ่ม "ออกจากระบบ" อยู่ในหน้าโปรไฟล์)

**บัญชีผู้ดูแลระบบ** — ชื่อผู้ใช้ `admin`
รหัสผ่านไม่ได้เขียนไว้ในไฟล์ใดของโปรเจกต์ เพื่อไม่ให้หลุดตอนขึ้นโฮสต์
ถ้าลืม ให้ตั้งใหม่ตามวิธีใน `docs/hosting.md` หัวข้อ 4.1

**บัญชีผู้ใช้ทั่วไป** — ไม่มีมาให้ ต้องกด "สมัครสมาชิก" ที่หน้าเข้าสู่ระบบ
(use case: `Register`) กรอกชื่อผู้ใช้ · ชื่อ-นามสกุล · รหัสนักศึกษา · รหัสผ่าน
ระบบสร้างอีเมลให้อัตโนมัติเป็น `s<รหัสนักศึกษา>@email.kmutnb.ac.th`
กติกาการกรอกอยู่ที่ `RZ.SIGNUP_RULES` ใน `config.js`

| ช่อง | กติกา |
|---|---|
| ชื่อผู้ใช้ | 4-20 ตัว เฉพาะ `a-z` `0-9` `.` `_` และห้ามซ้ำกับคนอื่น |
| รหัสนักศึกษา/บุคลากร | ตัวเลข 8-13 หลัก |
| รหัสผ่าน | อย่างน้อย 8 ตัวอักษร และต้องกรอกยืนยันให้ตรงกัน |

สมัครใหม่ได้บทบาท `user` เท่านั้น — **ไม่มีทางสมัครเป็น admin ได้**
บัญชี admin สร้างด้วยมือในฐานข้อมูล (`api/register.php` เขียน `role='user'` ตายตัว)

กรอกผิดจะขึ้นข้อความ "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง" เหมือนกันทั้งกรณีชื่อผิดและรหัสผิด
เพื่อไม่ให้เดาได้ว่าชื่อผู้ใช้ไหนมีอยู่ในระบบ

> ⚠️ ต้นแบบเก็บบัญชีที่สมัครไว้ใน **localStorage ของเบราว์เซอร์** และเทียบรหัสผ่านตรง ๆ
> ด้วย JavaScript เพื่อให้สาธิตได้โดยไม่ต้องมีเซิร์ฟเวอร์ (รีเฟรชแล้วบัญชียังอยู่
> แต่ย้ายเครื่องหรือเปลี่ยนเบราว์เซอร์แล้วหาย) **ระบบจริงห้ามทำแบบนี้**
> เพราะเปิด DevTools ก็อ่านรหัสผ่านได้ทันที
> ต้องให้ `api/register.php` เก็บด้วย `password_hash()` และ `api/auth.php`
> ตรวจด้วย `password_verify()` แล้วอ่าน `role` จากตาราง `users`
> — โค้ด PHP ทั้งสองไฟล์เขียนไว้ให้แล้ว เหลือแค่เปิด `fetch()` ที่คอมเมนต์ไว้ใน `auth.js`

| | ผู้ใช้ทั่วไป (user) | ผู้ดูแลระบบ (admin) |
|---|---|---|
| แผนที่พื้นที่เสี่ยง | ✅ เห็นเฉพาะรายงานที่อนุมัติแล้ว | ✅ |
| แจ้งเหตุการณ์ · รายงานของฉัน · การแจ้งเตือน | ✅ | ⛔ |
| คิวรอตรวจสอบ (อนุมัติ / ไม่อนุมัติ) | ⛔ | ✅ |
| รายงานทั้งหมด (เปลี่ยนสถานะ / ลบ) | ⛔ | ✅ |
| ความคิดเห็นทั้งหมด (ซ่อน) | ⛔ | ✅ |
| ผู้ใช้ระบบ (ระงับ / ปลดระงับบัญชี) | ⛔ | ✅ |
| ประวัติการจัดการ | ⛔ | ✅ |

**สิ่งที่ต้องเข้าใจให้ตรงกันในกลุ่ม** — `data-role` ใน HTML และการเช็ค role ใน JavaScript
เป็นแค่การ **"จัดหน้าจอ"** ไม่ใช่การรักษาความปลอดภัย
ใครเปิด DevTools แล้วสั่ง `RZ.go("admin-users")` ก็เข้าหน้านั้นได้
สิ่งที่กันได้จริงคือ `require_role('admin')` ใน `api/admin.php` ที่ทำงานฝั่งเซิร์ฟเวอร์

**การกระทำที่กระทบผู้ใช้ ต้องกรอกเหตุผลทุกครั้ง** — ไม่อนุมัติ · ลบรายงาน · ซ่อนความคิดเห็น ·
ระงับบัญชี ทั้ง 4 อย่างบังคับกรอกเหตุผล และถูกบันทึกลงตาราง `admin_audit_logs`
ดูได้ที่หน้า "ประวัติการจัดการ" ของฝั่งผู้ดูแลระบบ
(ตารางสิทธิ์เต็มและการไหลของสถานะอยู่ใน `docs/permissions.md`)

## 6. หลักการที่ใช้ในโค้ดนี้ (ตอบอาจารย์ได้)

**1) แยกตามหน้าที่ ไม่แยกตามหน้าจอ**
CSS แยกเป็น tokens → base → layout → components (ลำดับสำคัญ ห้ามสลับ)
JS แยกเป็นโมดูลตามความรับผิดชอบ 1 ไฟล์ = 1 เรื่อง

**2) ทุกไฟล์แชร์ข้อมูลกันผ่านตัวแปรเดียวชื่อ `RZ`**
ทำให้ไม่ต้องใช้ระบบ module และไม่มีตัวแปร global เกลื่อน
ทุกไฟล์เริ่มด้วย `window.RZ = window.RZ || {};`

**3) หน้าเว็บไม่แตะข้อมูลตรง ๆ**
`map.js`, `reports.js`, `form.js` เรียกผ่าน `RZ.api.xxx()` เท่านั้น
เวลาเปลี่ยนจากข้อมูลตัวอย่างไปเป็น MySQL จึงแก้แค่ `api.js` ไฟล์เดียว
(หลักการ separation of concerns — เอาไปเขียนในรายงานได้)

**4) ระวังชื่อคลาส CSS ชนกัน**
เคยเกิดขึ้นจริงในโปรเจกต์นี้: คลาส `.done` ถูกใช้ทั้งกับการ์ด "ส่งรายงานสำเร็จ"
และกับขั้นที่ผ่านแล้วในแถบติดตามสถานะ ทำให้มีกรอบสี่เหลี่ยมโผล่มาครอบแต่ละขั้น
แก้โดยเปลี่ยนการ์ดหน้าสำเร็จเป็น `.successbox`
บทเรียน: ตั้งชื่อคลาสให้บอกว่าเป็น "ชิ้นส่วนอะไร" ไม่ใช่ "สถานะอะไร" เฉย ๆ

**5) ไลบรารีภายนอกตั้ง z-index เองได้ ต้องขังไว้ในกล่องของมัน**
Leaflet ตั้ง z-index ให้ชั้นข้างในตัวเองสูงถึง 400-800 ตอนแรกกล่องแผนที่ไม่มี
z-index ของตัวเอง จึงไม่เป็น stacking context ชั้นข้างในก็หลุดไปเทียบกับทั้งหน้าเว็บ
แล้วลอยขึ้นมาทับหน้าเข้าสู่ระบบทุกหน้า แก้โดยใส่ `isolation:isolate` ที่ `.mapwrap`
บทเรียน: ครอบไลบรารีภายนอกด้วยกล่องที่เป็น stacking context เสมอ

**6) "ของฉัน" ต้องกรองด้วยตัวตนคนที่ล็อกอิน ไม่ใช่ธงในข้อมูล**
เดิมข้อมูลจำลองติดธง `mine: true` ไว้ 3 ใบ ใครล็อกอินเข้ามาก็เห็นรายงานของคนอื่น
เป็นของตัวเอง แก้ให้ `getMyReports()` / `getAlerts()` กรองด้วย `RZ.session.userId`
ตรงกับ `WHERE user_id = ?` ในฐานข้อมูล และ `createReport()` ประทับเจ้าของจาก session
บทเรียน: ข้อมูลส่วนตัวต้องผูกกับ "ใคร" ทุกแถว และ id นั้นต้องมาจากฝั่งเซิร์ฟเวอร์

**7) ข้อมูลที่ต้องอยู่ข้ามการรีเฟรช ต้องมีที่เก็บ**
เดิมรายงานที่ส่งใหม่อยู่ใน `RZ.DATA` ซึ่งเป็นตัวแปรในหน่วยความจำ รีเฟรชหน้าเดียวหายหมด
ตอนสาธิตดูเหมือนส่ง 3 ใบขึ้นใบเดียว แก้โดยเก็บสำเนาลง localStorage
(`RZ.api._save()` ท้ายทุกฟังก์ชันที่เปลี่ยนข้อมูล) — พอต่อ MySQL แล้วลบส่วนนี้ออกได้
บทเรียน: แยกให้ชัดว่าอะไรคือ "สถานะชั่วคราวของหน้าจอ" กับอะไรคือ "ข้อมูลที่ต้องเก็บ"

**8) ฟอร์มต้องล้างตัวเองเมื่อเริ่มใบใหม่**
ค่าที่ค้างจากใบก่อนทำให้ผู้ใช้ส่งข้อมูลผิดโดยไม่รู้ตัว
แก้โดยเรียก `RZ.resetForm()` ทั้งตอนส่งสำเร็จและตอนเข้าหน้าฟอร์ม (ใน `router.js`)
บทเรียน: ล้างที่ "ตอนเข้า" ไม่ใช่แค่ "ตอนออก" เพราะผู้ใช้กดออกกลางทางได้

**9) อย่าออกเลข id ด้วยตัวนับตายตัว**
`nextNo: 143` ชนกับรายงานเดิมที่มีเลขถึง 148 ทำให้ `findIncident()` เจอใบเก่าก่อน
พอแอดมินกดอนุมัติ สถานะจึงไปเปลี่ยนผิดใบ และแจ้งเตือนไปถึงคนผิด
แก้เป็น `RZ.nextReportNo()` ที่คำนวณจากเลขสูงสุดที่มีอยู่ +1
บทเรียน: id ต้องรับประกันว่าไม่ซ้ำ (ของจริงใช้ `AUTO_INCREMENT`)

## 7. ขั้นตอนต่อ PHP + MySQL

**7.1 ติดตั้งและวางไฟล์**

1. ติดตั้ง XAMPP แล้วเปิด Apache + MySQL
2. คัดลอกโฟลเดอร์นี้ไปที่ `C:\xampp\htdocs\redzone`
3. เปิด `http://localhost/redzone/` — เว็บต้องทำงานเหมือนเดิม

**7.2 สร้างฐานข้อมูล**

1. เปิด `http://localhost/phpmyadmin`
2. นำเข้า `database/schema.sql` (สร้างตาราง)
3. นำเข้า `database/seed.sql` (ข้อมูลตั้งต้น)
4. แก้รหัสฐานข้อมูลใน `api/config/db.php` ถ้าไม่ใช่ค่าเริ่มต้นของ XAMPP

**7.3 ทดสอบ API ก่อนแก้หน้าเว็บ**

เปิด `http://localhost/redzone/api/incidents.php` ต้องเห็น JSON
ถ้าเห็น error ให้แก้ให้ผ่านก่อน อย่าไปแก้ JavaScript

**7.4 สลับให้หน้าเว็บใช้ฐานข้อมูล**

เปิด `assets/js/api.js` — ในแต่ละฟังก์ชันมีโค้ด `fetch()` คอมเมนต์ไว้อยู่แล้ว
เปิดใช้ทีละฟังก์ชัน แล้วทดสอบทีละอัน

> ⚠️ `fetch()` ทำงานแบบ asynchronous ผู้เรียกต้องเปลี่ยนเป็น `async/await` ด้วย
> เช่นใน `map.js` เปลี่ยน `var list = RZ.api.getIncidents();`
> เป็น `var list = await RZ.api.getIncidents();` และประกาศฟังก์ชันเป็น `async`
> แนะนำให้เริ่มจาก `getIncidents` ตัวเดียวให้ผ่านก่อน แล้วค่อยทำตัวอื่น

**7.5 สิ่งที่ยังต้องทำเพิ่มถ้าจะใช้งานจริง**

ยึดตาม use case diagram ของกลุ่ม

- [x] `Register` — หน้าสมัครสมาชิก + `api/register.php` (ต้นแบบเก็บใน localStorage)
- [x] `log in` — ล็อกอินด้วยชื่อผู้ใช้ + `api/auth.php`
- [x] `report approved` / `report reject` · `delete report` · `delete comment` · `ban user`
      — ทำหน้าจอและ `api/admin.php` ไว้แล้ว เหลือแค่เปิดใช้ `fetch()` ใน `api.js`
- [ ] อัปโหลดรูปภาพจริง (`report_attachments` + โฟลเดอร์ `uploads/`)
- [ ] ตรวจสิทธิ์ตาม role ทุกไฟล์ใน `api/` (ตอนนี้ยังไม่ตรวจ)

## 8. ข้อควรระวัง

- **ข้อมูลในเว็บตอนนี้เป็นข้อมูลสมมติทั้งหมด** ชื่ออาคาร เหตุการณ์ และชื่อผู้เขียนความคิดเห็นแต่งขึ้นเพื่อนำเสนอ
- ต้นแบบมีบางส่วนที่ **ไม่มีใน use case diagram** (ติดตามสถานะ, การแจ้งเตือน, กดยืนยัน, ตั้งค่าโปรไฟล์) — ต้องตัดสินใจว่าจะเพิ่มใน diagram หรือตัดออกจากต้นแบบ ดูตารางเทียบใน `docs/structure.md` หัวข้อ 2
- ลำดับ `<script>` ใน `index.html` **ห้ามสลับ** `main.js` ต้องอยู่ท้ายสุด
- ลำดับ `<link>` CSS ก็ห้ามสลับ `tokens.css` ต้องมาก่อน
- ฟอนต์และแผนที่โหลดจากอินเทอร์เน็ต ถ้าออฟไลน์เว็บยังใช้ได้แต่หน้าตาจะเปลี่ยนและไม่มีแผนที่
- อย่า commit `api/config/db.php` ขึ้น GitHub ถ้าใส่รหัสจริง (มีใน `.gitignore` แล้ว)
