# RedZone — การเก็บข้อมูล สิทธิ์การใช้งาน และการเข้าถึงของผู้ดูแลระบบ

เอกสารนี้ตอบ 3 คำถาม: ข้อมูลเก็บที่ไหนอย่างไร · ใครทำอะไรได้ · admin เข้าถึงระบบอย่างไร
เอาไปวางในบท "การออกแบบระบบ" และ "การควบคุมความปลอดภัย" ของรายงานได้

> **สถานะปัจจุบันของต้นแบบ** — ทำเสร็จแล้วทั้ง 2 ฝั่ง
> · ฝั่ง `user` : แผนที่ · แจ้งเหตุ · ติดตามสถานะ · คอมเมนต์ · แจ้งเตือน · โปรไฟล์
> · ฝั่ง `admin` : คิวรอตรวจสอบ · รายงานทั้งหมด · ความคิดเห็น · ผู้ใช้ระบบ · ประวัติการจัดการ
> · ฝั่ง PHP : `api/admin.php` มี `require_role('admin')` และเขียน `admin_audit_logs` แล้ว
>
> เปิดเว็บมาต้องเข้าสู่ระบบก่อนทุกครั้ง ไม่มีทางลัดสำหรับสาธิต
> · ผู้ดูแลระบบ : ชื่อผู้ใช้ `admin` (บัญชีเดียวในระบบ · รหัสผ่านไม่ได้เก็บไว้ในไฟล์)
> · ผู้ใช้ทั่วไป : ไม่มีมาให้ ต้องกด "สมัครสมาชิก" เอง (use case `Register`)
> บทบาทมาจากบัญชีที่ล็อกอินสำเร็จ ผู้ใช้เลือกเองไม่ได้ และสมัครใหม่ได้ `user` เท่านั้น
> สิ่งที่ยังเหลือดูหัวข้อ 7

## 2. ฐานข้อมูลเก็บอะไรไว้ที่ไหน

12 ตาราง แบ่งได้เป็น 5 กลุ่มตามหน้าที่

### กลุ่ม 1 — ผู้ใช้และสิทธิ์

| ตาราง | เก็บอะไร | คอลัมน์ที่สำคัญต่อสิทธิ์ |
|---|---|---|
| `users` | บัญชีผู้ใช้ทุกคน | **`role`** = `user` หรือ `admin` · **`is_active`** = 0 คือถูกระงับ · `ban_reason` · `password_hash` |
| `user_settings` | การตั้งค่าส่วนตัว 1:1 กับ users | `always_anonymous`, `notify_*`, `share_location` |

`role` และ `is_active` สองคอลัมน์นี้เป็นหัวใจของระบบสิทธิ์ทั้งหมด
โค้ดฝั่ง PHP จะอ่านสองค่านี้ทุกครั้งที่มีคนขออะไร

### กลุ่ม 2 — ข้อมูลอ้างอิง (ไม่ค่อยเปลี่ยน)

| ตาราง | เก็บอะไร | ใครแก้ได้ |
|---|---|---|
| `categories` | ประเภทเหตุการณ์ 7 แบบ | admin |
| `locations` | สถานที่ในรัศมี 10 กม. + latitude/longitude | admin |
| `zones` | พื้นที่เสี่ยง : จุดศูนย์กลาง + รัศมี (เมตร) + จำนวนรายงาน | admin |

### กลุ่ม 3 — รายงานและของที่พ่วงมา (ตารางหลักของระบบ)

| ตาราง | เก็บอะไร |
|---|---|
| `reports` | รายงาน 1 แถว = 1 เหตุการณ์ · `status` คือสถานะปัจจุบัน · `user_id` เป็น NULL ได้ |
| `report_attachments` | รูปภาพแนบ เก็บแค่ path ไฟล์จริงอยู่ในโฟลเดอร์ `uploads/` |
| `report_status_logs` | ประวัติการเปลี่ยนสถานะทุกครั้ง ใครเปลี่ยน เปลี่ยนเมื่อไหร่ |
| `report_confirmations` | ใครกด "ฉันพบเหตุนี้ด้วย" — `PRIMARY KEY (report_id, user_id)` กันกดซ้ำ |
| `comments` | ความคิดเห็น · `is_hidden` = ถูกลบแบบ soft delete · `hidden_by` = admin ที่กดลบ |

### กลุ่ม 4 — การแจ้งเตือน

| ตาราง | เก็บอะไร |
|---|---|
| `notifications` | ข้อความแจ้งเตือนรายคน · `is_read` · `ref_report_id` ชี้กลับไปที่รายงาน |

### กลุ่ม 5 — การตรวจสอบย้อนหลัง

| ตาราง | เก็บอะไร |
|---|---|
| `admin_audit_logs` | ทุกการกระทำของผู้ดูแลระบบ : ใครทำ · ทำอะไร · กับอะไร · เพราะอะไร · เมื่อไหร่ |

## 3. ข้อมูล 1 รายงานเดินทางผ่านตารางไหนบ้าง

ตัวอย่าง: นักศึกษาแจ้ง "ไฟทางดับ" แบบ**เปิดเผยชื่อ** แล้ว admin อนุมัติ

| ลำดับ | เกิดอะไร | ตารางที่ถูกเขียน |
|---|---|---|
| 1 | นักศึกษากดส่งฟอร์ม | `reports` (1 แถว, `status='sent'`, `user_id=15`) |
| 2 | ระบบแนบรูป 2 รูป | `report_attachments` (2 แถว) |
| 3 | ระบบบันทึกสถานะแรก | `report_status_logs` (`NULL → sent`) |
| 4 | ระบบแจ้ง admin | `notifications` (แถวของ admin) |
| 5 | admin กดอนุมัติ | `reports.status = 'ack'` + `report_status_logs` (`sent → ack`, `changed_by=2`) |
| 6 | ระบบแจ้งผู้แจ้งกลับ | `notifications` (แถวของ user 15) |
| 7 | คนอื่นกดยืนยัน 3 คน | `report_confirmations` (3 แถว) + `reports.confirm_count = 3` |
| 8 | คนอื่นคอมเมนต์ | `comments` |

**จุดที่ต้องอธิบายในรายงาน** — สถานะเก็บ 2 ที่โดยเจตนา
`reports.status` เก็บ "สถานะตอนนี้" ไว้อ่านเร็ว
`report_status_logs` เก็บ "ประวัติทุกครั้งที่เปลี่ยน" ไว้ตรวจย้อนหลัง
ถ้าเก็บที่เดียวจะเสียอย่างใดอย่างหนึ่งไป

## 4. การแจ้งแบบไม่เปิดเผยชื่อ เก็บอย่างไร

นี่คือจุดที่ต้องออกแบบให้ชัด เพราะเป็นเรื่องความเป็นส่วนตัว

| กรณี | `reports.user_id` | `reports.is_anonymous` | admin เห็นอะไร |
|---|---|---|---|
| แจ้งเปิดเผยชื่อ | `15` | `0` | ชื่อ · รหัสนักศึกษา · อีเมล |
| แจ้งไม่เปิดเผยชื่อ | `NULL` | `1` | เห็นแค่เนื้อหารายงาน ไม่รู้ว่าใครแจ้ง |

**ทำไม `user_id` ต้องเป็น NULL ไม่ใช่เก็บไว้แล้วแค่ไม่แสดง**
ถ้าเก็บ `user_id` ไว้แล้วอาศัยว่าโค้ดจะไม่แสดง — ใครที่เข้า phpMyAdmin ได้
ก็เห็นว่าใครแจ้งทันที ความไม่เปิดเผยชื่อจึงไม่จริง
การเก็บเป็น NULL คือการรับประกันในระดับโครงสร้างข้อมูล ไม่ใช่ระดับโค้ด

**ผลข้างเคียงที่ต้องยอมรับ** — เมื่อ `user_id` เป็น NULL ระบบจะส่งการแจ้งเตือน
กลับไปหาผู้แจ้งไม่ได้ (เพราะไม่รู้ว่าใคร) ต้นแบบนี้จึงบังคับให้เปิด
"รับการติดต่อกลับทางอีเมล" ไว้ตลอด และเก็บอีเมลไว้ในตาราง `notifications`
ในรูปข้อความแจ้งเตือนแทน — ระบบส่งให้ ส่วน admin ไม่เห็นว่าเป็นใคร

## 5. ใครมีสิทธิ์ทำอะไรบ้าง

### 5.1 Actor ตาม use case diagram

| Actor | คือใคร | `users.role` |
|---|---|---|
| **new user** | คนที่ยังไม่มีบัญชี | (ยังไม่มีแถวใน `users`) |
| **User** | นักศึกษา/บุคลากรที่ล็อกอินแล้ว | `user` |
| **admin** | ผู้ดูแลระบบ — ตรวจรายงานและดูแลผู้ใช้ | `admin` |
| **System** | ตัวระบบเอง ไม่ใช่คน (ส่งการแจ้งเตือน คำนวณพื้นที่เสี่ยง) | — |

**มี 2 บทบาทเท่านั้น** ตรงกับ use case diagram
`users.role` เป็น `ENUM('user','admin')` ไม่มีบทบาท `officer` แยก —
งานตรวจสอบและงานดูแลผู้ใช้อยู่ที่ `admin` ทั้งหมด

### 5.2 ตารางสิทธิ์ (Permission Matrix)

✅ = ทำได้ · ⛔ = ทำไม่ได้ · 🔸 = ทำได้เฉพาะของตัวเอง

| การกระทำ | ยังไม่ล็อกอิน | User | admin | ตารางที่เกี่ยวข้อง |
|---|---|---|---|---|
| สมัครสมาชิก (ได้บทบาท `user` เท่านั้น) | ✅ | ⛔ | ⛔ | `users`, `user_settings` |
| เข้าสู่ระบบด้วยชื่อผู้ใช้ + รหัสผ่าน | ✅ | — | ✅ | `users` |
| สมัครบัญชีให้ตัวเองเป็น `admin` | ⛔ | ⛔ | ⛔ | — (สร้างด้วยมือในฐานข้อมูล) |
| ดูแผนที่และเหตุการณ์ที่อนุมัติแล้ว | ⛔ | ✅ | ✅ | `reports`, `zones` |
| ดูเหตุการณ์ที่ยังไม่อนุมัติ | ⛔ | ⛔ | ✅ | `reports` |
| แจ้งเหตุการณ์ใหม่ | ⛔ | ✅ | ✅ | `reports`, `report_attachments` |
| ดูชื่อผู้แจ้ง (กรณีไม่ได้แจ้งแบบไม่เปิดเผยชื่อ) | ⛔ | ⛔ | ✅ | `users` |
| ติดตามสถานะรายงาน | ⛔ | 🔸 ของตัวเอง | ✅ ทุกรายงาน | `reports`, `report_status_logs` |
| กดยืนยัน "พบเหตุนี้ด้วย" | ⛔ | ✅ (1 ครั้ง/รายงาน) | ✅ | `report_confirmations` |
| เขียนความคิดเห็น | ⛔ | ✅ | ✅ | `comments` |
| ลบความคิดเห็น | ⛔ | 🔸 ของตัวเอง | ✅ ทุกอัน | `comments.is_hidden` |
| **อนุมัติรายงาน** (report approved) | ⛔ | ⛔ | ✅ | `reports.status`, `report_status_logs` |
| **ปฏิเสธรายงาน** (report reject) | ⛔ | ⛔ | ✅ | `reports.status`, `report_status_logs` |
| **ลบรายงาน** (delete report) | ⛔ | ⛔ | ✅ | `reports` |
| **ระงับบัญชีผู้ใช้** (ban user) | ⛔ | ⛔ | ✅ | `users.is_active = 0` |
| กำหนด/แก้พื้นที่เสี่ยง | ⛔ | ⛔ | ✅ | `zones` |
| เพิ่ม/ลบประเภทเหตุการณ์ | ⛔ | ⛔ | ✅ | `categories` |
| แก้โปรไฟล์และการตั้งค่าของตัวเอง | ⛔ | ✅ | ✅ | `users`, `user_settings` |
| แก้โปรไฟล์ของคนอื่น | ⛔ | ⛔ | ✅ | `users` |
| อ่านการแจ้งเตือน | ⛔ | 🔸 ของตัวเอง | 🔸 ของตัวเอง | `notifications` |
| เข้า phpMyAdmin / แตะฐานข้อมูลตรง ๆ | ⛔ | ⛔ | ✅ (ผู้ดูแลเซิร์ฟเวอร์) | ทุกตาราง |

### 5.3 สิ่งที่ **ไม่มีใคร** ทำได้ (ออกแบบไว้ให้ทำไม่ได้)

| ทำไม่ได้ | เหตุผล |
|---|---|
| ดูรหัสผ่านของผู้ใช้ | ฐานข้อมูลเก็บแค่ hash จาก `password_hash()` ถอดกลับไม่ได้ |
| รู้ว่าใครแจ้งรายงานแบบไม่เปิดเผยชื่อ | `user_id` เป็น NULL ไม่มีข้อมูลให้ดู แม้แต่ admin |
| ลบความคิดเห็นให้หายไปจากฐานข้อมูลจริง | ใช้ `is_hidden` (soft delete) เพื่อให้ตรวจย้อนหลังได้ว่าใครลบอะไร |
| กดยืนยันรายงานเดิมซ้ำเพื่อปั่นตัวเลข | `PRIMARY KEY (report_id, user_id)` บล็อกไว้ที่ระดับฐานข้อมูล |
| แจ้งเหตุนอกรัศมี 10 กม. | ตรวจพิกัดก่อนบันทึก (ต้องตรวจซ้ำที่ PHP ด้วย ไม่ใช่แค่ JS) |

## 6. การไหลของสถานะรายงาน (report approved / report reject)

```
   นักศึกษาส่งรายงาน
          │
          ▼
      [ sent ]  รอตรวจสอบ  ← ยังไม่ขึ้นบนแผนที่สาธารณะ
          │
    ┌─────┴─────────────────────┐
    │ admin กดอนุมัติ            │ admin กดไม่อนุมัติ (ต้องมีเหตุผล)
    ▼                           ▼
[ ack ] รับเรื่องแล้ว        [ reject ] ไม่อนุมัติ
    │   ← เริ่มขึ้นแผนที่          │   ← ไม่ขึ้นแผนที่ ผู้แจ้งเห็นเหตุผล
    ▼                           └─ จบ (ผู้ใช้แก้ข้อมูลแล้วแจ้งใหม่ได้)
[ prog ] กำลังดำเนินการ
    │
    ▼
[ done ] เสร็จสมบูรณ์
```

**จุดที่ต้องอธิบายในรายงาน** — เหตุผลที่ต้องมีสถานะ `sent` คั่นก่อนขึ้นแผนที่
ถ้าให้รายงานขึ้นแผนที่ทันทีที่ส่ง ใครก็ปั่นข้อมูลเท็จให้พื้นที่ดูอันตรายได้
การมีคนกลางตรวจก่อน (`report approved`) คือกลไกรักษาความน่าเชื่อถือของข้อมูล

ทุกครั้งที่สถานะเปลี่ยน ระบบเขียน 3 ที่พร้อมกันในทรานแซกชันเดียว
`reports.status` · `report_status_logs` (ประวัติ) · `notifications` (แจ้งผู้แจ้ง)
ถ้ารายงานนั้นแจ้งแบบไม่เปิดเผยชื่อ (`user_id` เป็น NULL) จะข้ามการแจ้งเตือนไป
เพราะไม่มีข้อมูลว่าต้องส่งให้ใคร

## 7. admin เข้าถึงระบบอย่างไร

### 7.1 ขั้นตอนตอนล็อกอิน

```
admin กรอกชื่อผู้ใช้ + รหัสผ่าน  (หน้าเดียวกับผู้ใช้ทั่วไป ไม่ต้องมี URL ลับ)
        │
        ▼
api/auth.php
  1. SELECT role, is_active, password_hash FROM users WHERE username = ?
  2. password_verify()  ← ตรวจรหัสผ่านที่ฝั่งเซิร์ฟเวอร์เท่านั้น
  3. ถ้า is_active = 0  → ปฏิเสธ (นี่คือกลไกที่ทำให้ ban user มีผลจริง)
  4. session_regenerate_id(true)   ← กัน session fixation
  5. $_SESSION['user_id'] = ...  และ  $_SESSION['role'] = 'admin'
        │
        ▼
หน้าเว็บอ่าน role ที่ตอบกลับมา แล้วพาไปที่ /admin/
```

**ทำไมไม่ทำหน้า login แยกสำหรับ admin** — URL ลับไม่ใช่การรักษาความปลอดภัย
สิ่งที่กันได้จริงคือการตรวจ `role` ที่ฝั่งเซิร์ฟเวอร์ทุกครั้งที่มีคำขอเข้ามา

**ทำไมข้อความ error ต้องเหมือนกันทั้งกรณีชื่อผู้ใช้ผิดและรหัสผ่านผิด**
ถ้าแยกข้อความ ("ไม่พบผู้ใช้นี้" กับ "รหัสผ่านผิด") คนที่ลองเดาจะรู้ทันทีว่า
ชื่อผู้ใช้ไหนมีอยู่จริงในระบบ แล้วไปโฟกัสเดารหัสผ่านของบัญชีนั้นต่อ
ยกเว้นกรณี **บัญชีถูกระงับ** ที่บอกได้ เพราะผ่านการตรวจรหัสผ่านมาแล้ว

### 7.2 การตรวจสิทธิ์ในทุกไฟล์ที่ admin ใช้

ทำไว้แล้วใน `api/config/db.php` (ฟังก์ชัน `require_login()` และ `require_role()`)
และ `api/admin.php` เรียกใช้ตั้งแต่บรรทัดแรก

```php
<?php
require __DIR__ . '/config/db.php';

$adminId = require_role('admin');   // ★ ไม่ผ่าน = จบด้วย HTTP 403 ทันที

/* ...จากนี้ถึงจะทำงานของ admin ได้... */
```

ไฟล์อื่นใน `api/` ใช้ `require_login()` ซึ่งคืนค่า `user_id` จาก session มาให้
ทำให้ไม่ต้องฮาร์ดโค้ด `$userId = 1` อีก

หลักที่ต้องยึด: **ตรวจที่ทางเข้าข้อมูล ไม่ใช่ที่หน้าจอ**
ถ้าลืมใส่ `require_role()` แม้แต่ไฟล์เดียว นักศึกษาคนไหนก็ยิงเข้ามาลบรายงานได้

### 7.3 การเข้าถึงฐานข้อมูลตรง ๆ

| ช่องทาง | ใครใช้ | ใช้ทำอะไร |
|---|---|---|
| หน้าเว็บ `/admin/` | admin | งานประจำวัน — อนุมัติ ปฏิเสธ ลบ ระงับบัญชี |
| phpMyAdmin | ผู้ดูแลเซิร์ฟเวอร์ | นำเข้าสคีมา · แก้ข้อมูลอ้างอิง · กู้ข้อมูล |
| บัญชี MySQL ของแอป | โค้ด PHP เท่านั้น | ควรเป็นบัญชีที่ให้สิทธิ์เท่าที่จำเป็น ไม่ใช่ `root` |

**ข้อควรทำในระบบจริง** — สร้างบัญชี MySQL แยกให้แอป ไม่ใช้ `root`

```sql
CREATE USER 'redzone_app'@'localhost' IDENTIFIED BY 'รหัสที่ยาวและเดายาก';
GRANT SELECT, INSERT, UPDATE ON redzone.* TO 'redzone_app'@'localhost';
-- ไม่ให้ DELETE เลย เพราะระบบใช้ soft delete อยู่แล้ว
-- ไม่ให้ DROP / ALTER เพราะแอปไม่ต้องแก้โครงสร้างตาราง
```

ต้นแบบตอนนี้ตั้งไว้เป็น `root` รหัสว่างตามค่าเริ่มต้นของ XAMPP
ซึ่ง**ใช้ได้แค่บนเครื่องตัวเองตอนทำโปรเจกต์** ห้ามเอาขึ้นเซิร์ฟเวอร์จริง

## 8. ช่องโหว่ที่ยังเหลืออยู่ในต้นแบบ

พูดตรง ๆ ว่ายังไม่ได้ทำ ดีกว่าให้อาจารย์จับได้เอง

| เรื่อง | สถานะ | หมายเหตุ |
|---|---|---|
| หน้าจอฝั่ง admin | ✅ ทำแล้ว | 5 หน้า อยู่ใน `index.html` + `assets/js/admin.js` |
| `require_role()` ฝั่ง PHP | ✅ ทำแล้ว | `api/config/db.php` + เรียกใน `api/admin.php` |
| ตาราง `admin_audit_logs` | ✅ ทำแล้ว | บันทึกทุกการกระทำพร้อมเหตุผล |
| บังคับกรอกเหตุผล | ✅ ทำแล้ว | ไม่อนุมัติ · ลบรายงาน · ซ่อนคอมเมนต์ · ระงับบัญชี |
| กันแอดมินระงับบัญชีตัวเอง | ✅ ทำแล้ว | ตรวจทั้งฝั่ง JS และฝั่ง PHP |
| หน้าสมัครสมาชิก (Register) | ✅ ทำแล้ว | หน้าจอใน `index.html` + `api/register.php` |
| กันสมัครเป็น admin | ✅ ทำแล้ว | `register.php` เขียน `role='user'` ตายตัว ไม่รับค่าจากผู้ใช้ |
| ต้นแบบเก็บรหัสผ่านเป็นข้อความเปล่า | ⚠️ โดยเจตนา | เก็บใน localStorage เพื่อสาธิตโดยไม่ต้องมีเซิร์ฟเวอร์ — `register.php` ของจริงใช้ `password_hash()` แล้ว |
| ตรวจรัศมี 10 กม. ที่ฝั่ง PHP | ❌ ตรวจแค่ใน JS | เพิ่มการคำนวณระยะใน `reports.php` ก่อน INSERT |
| ยืนยันตัวตนว่าเป็นคน มจพ. จริง | ❌ ยังไม่มี | ส่งลิงก์ยืนยันไปที่อีเมลมหาวิทยาลัย ก่อนเปิดใช้บัญชี |
| อัปโหลดรูปจริง | ❌ ยังไม่มี | ตรวจชนิดไฟล์ · เปลี่ยนชื่อไฟล์ · จำกัดขนาด · เก็บใน `uploads/` |
| จำกัดจำนวนครั้งที่ล็อกอินผิด | ❌ ยังไม่มี | นับความพยายามต่อ IP/ชื่อผู้ใช้ แล้วหน่วงเวลา |
| HTTPS | ❌ ยังเป็น http บน localhost | ระบบจริงต้องเป็น https ไม่งั้นรหัสผ่านวิ่งเป็นข้อความเปล่า |

**ตาราง `admin_audit_logs` ที่เพิ่มเข้าไปแล้ว** (อยู่ใน `schema.sql`)

```sql
CREATE TABLE admin_audit_logs (
  log_id      INT AUTO_INCREMENT PRIMARY KEY,
  admin_id    INT          NOT NULL,          -- ใครทำ
  action      VARCHAR(50)  NOT NULL,          -- approve_report / reject_report /
                                              -- delete_report / hide_comment / ban_user
  target_type VARCHAR(30)  NOT NULL,          -- report / comment / user
  target_id   INT          NOT NULL,          -- id ของสิ่งที่ถูกกระทำ
  reason      VARCHAR(255),                   -- เหตุผล (ควรบังคับกรอกตอนลบหรือ ban)
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_audit_admin FOREIGN KEY (admin_id) REFERENCES users(user_id),
  INDEX idx_audit_admin (admin_id, created_at)
) ENGINE=InnoDB;
```

เหตุผลที่ต้องมี: `delete report` และ `ban user` เป็นการกระทำที่กระทบผู้ใช้โดยตรง
ถ้าไม่มีบันทึกไว้ ก็ตอบไม่ได้ว่าใครสั่ง และตรวจการใช้อำนาจเกินไม่ได้
ในต้นแบบดูได้ที่หน้า "ประวัติการจัดการ" ของฝั่งผู้ดูแลระบบ
